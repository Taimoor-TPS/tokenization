2. Token Requestor — how configured & how identified

Path: Master Configuration › Wallet Configuration › Token Requestor

Master list of wallets/merchants allowed to request tokens. Persisted as token-requestors.json.

FieldRole
Token requestor IDUnique 11-digit key (immutable after create)
NameDisplay / “Channel” on the token
TypeOEM wallet / Issuer wallet (HCE) / Merchant card-on-file
SchemesVISA / MC allowed
Token type02 SE or 03 HCE — written on token
Device typesMobile / Watch / Tablet for provisioning
Payment channelsPOS contactless / E-commerce
StatusEnabled / Disabled

Seed IDs: 40010075001 OEM Wallet (enabled); 40010075002 Bank App Wallet; 40010075003 Unapproved Wallet (disabled).

Identification: exact match on requestorId ↔ tokenRequestors[].id. No name/type lookup for decisions.

  1. Simulator picks wallet → sends that id as requestorId
  2. Eligibility: must exist, Enabled, support scheme, allow device type (if “Require approved requestor” on)
  3. Token create stores requestorId, channel = name, tokenType
  4. Payment: if “Validate token requestor ID” on, requestor must still be Enabled

3. How does back office know Google Pay’s tokenRequestorId is correct?

The bank does not invent or discover the ID from the cardholder session. It maintains an allowlist of scheme-assigned Token Requestor IDs.

  1. Scheme assigns the ID — Google/Apple register with Visa VTS / Mastercard MDES; network issues a fixed TR ID.
  2. Bank loads official list during tokenization onboarding into Token Requestor master.
  3. Provisioning: Wallet → Scheme → Issuer; scheme authenticates the wallet; issuer receives tokenRequestorId from the scheme.
  4. Check: “Is this ID on our approved Enabled list for this scheme/device?”

In this demo, IDs are entered manually (OEM Wallet stands in for Google/Apple-style wallets). Nothing connects to live VTS/MDES.

5. Eligibility, ID&V Risk (1–5), Step-up — connection

Confusion: scores 50/70 vs device score bands 1–5

They are different numbers for different jobs. Three sequential stages:

1. Eligibility Rules (checkboxes) → May this card be tokenized at all? → FAIL → NOT_ELIGIBLE | PASS → continue 2. ID&V Risk Rules (score 1–5 + reason codes) → GREEN → create token immediately → YELLOW → Step-up / OTP → RED → decline (no token) 3. Step-up and OTP (only if YELLOW) → OTP OK → create token | fail → stop 4. createToken stamps assurance → GREEN → Assurance without step-up (50) → YELLOW → Assurance after step-up (70)
NumberScreenMeaning
1–5ID&V Risk Rules › Device score bandsRisk score from scheme/wallet → maps to GREEN/YELLOW/RED
50 / 70Eligibility › ID&V defaultsToken assurance label after success — not the risk score

OTP is not checked against the 1–5 score. Risk Rules decide whether OTP is needed; Step-up screen defines how OTP works (length, validity, channels, Issuer vs Scheme).

Unlisted reason code decision (default YELLOW): colour when a reason code is missing/disabled in Reason code rules — still unrelated to 50/70.

Example: score 3 + NEW_DEVICE → YELLOW → OTP → token with assurance 70. Score 5, no bad reasons → GREEN → no OTP → assurance 50.

7. If I change 50/70 — what changes? Why isn’t it on the CMS step image?

Changing 50/70 in this demo: almost no behavioural change. Eligibility, colours, OTP, and payment decisions do not read this field. Only the number written on new tokens changes (visible in Token Management › View).

CMS “Record the token against the card” animation intentionally shows a short summary:

card, tokenReference, device, channel, status, tokenExpiry

Assurance is not listed in that UI box, but createToken still saves assurance on the token in the store. Open Token Management › View to see it.

9. Reason code rules (ID&V Risk Rules › Reason code rules)

Bank’s risk dictionary: maps scheme/wallet reason codes to GREEN / YELLOW / RED.

Code (seed)MeaningDecision
LONG_STANDING_ACCOUNTLong clean wallet historyGREEN
NEW_DEVICEDevice not seen beforeYELLOW
NEW_WALLET_ACCOUNTWallet account recently createdYELLOW
DEVICE_FLAGGEDDevice flagged by schemeRED
ACCOUNT_HIGH_RISKWallet account high riskRED

Purpose: control bank response to risk signals after eligibility. Combined with device score; most serious colour wins.

How bank knows codes: from Visa/Mastercard (or wallet) issuer documentation at onboarding — not invented per transaction. Demo codes are illustrative seeds; simulator checkboxes simulate “scheme sent these.”

10. Do Visa or Mastercard send reasonCodes?

Yes — the scheme (Visa VTS or Mastercard MDES) delivers risk inputs with the provisioning / approve-provisioning style request. Often the wallet originated the scores/codes; the scheme forwards them to the issuer. Bank only looks them up in Reason code rules.

13. Lifecycle Configuration — what is it for?

Path: Master Configuration › Lifecycle Configuration

Not used in provisioning / add-to-wallet. Used for token lifecycle after the token exists — Operations › Token Management.

ScreenUse
Reason CodesCodes offered when operator Suspend / Unsuspend / Delete / Activate a token
Card Status CascadeWhen operator changes card status, what happens to all tokens on that card

Important: Lifecycle Reason Codes (T, F, C, Z…) are not the same as ID&V reason codes (NEW_DEVICE, etc.).

Card Status Cascade (seed)

New card statusEffect on tokens
ACTIVEResume (only tokens with suspendedBy = CARD)
WARM / EXPIREDSuspend
HOT / BLOCKEDDelete

Scheme Cascade mode (Visa CARD_LEVEL / MC PER_TOKEN) controls how scheme calls are shown. Card status is changed from Token Management (not the Card master form) so cascade runs.

14. Token Management → Suspend → Reason Code dropdown

This flow exists in the portal code. It is easy to miss in the UI.

  1. Operations › Token Management
  2. Expand the card row (Tokens column ▸)
  3. On an ACTIVE token, click ✕ (Suspend) — icon only, not a text button
  4. Modal “Update Token Status” → Reason Code * dropdown filled from Lifecycle › Reason Codes via reasonCodesFor(action, scheme)
  5. Reason text (min 5 characters) → Continue → Confirm → TknEngine.lifecycle
If it seems missing: card not expanded; token not ACTIVE (Suspend disabled); looking at Simulator wallet Remove (cardholder delete — no operator reason-code dropdown); or looking only at Master Configuration screens (config only, no action).

Engine checks reason code enabled + applies to action + scheme, else REASON_CODE_INVALID.
